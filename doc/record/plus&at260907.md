# []+ が、 L1. や @1= の場合に使えない問題

## 問題点
    - []+ という記述方法は、次回の [] と文字列を繋げて、一つのメッセージにする仕様である
    - しかし、L1.[] のようにパート名が先頭にある場合、先にパートの処理をすると、+があった場合に次のメッセージまで待つ仕様とぶつかるため、現在は正常に動作しない

## 新仕様
    - 現状の仕様は、Part.[] の処理が、[]+ より先に行われるために起きてしまう
    - であれば、[]+ がある場合、先に []+ の処理を行い、内容をバッファに保持、次回の [] が来るまで待つ。
    - そのあと、Part.[] や @n= の処理に回せば、[]+ を使った長いメッセージの場合でも、その他の機能を使いやすくなることが想定できる


# @1= が特定パートにしか使えない問題

## 問題点
    - @1=[] という指示はパートを跨いで利用できない

## 新仕様
    - @1=[] と一度指定しておけば、{@1} を複数パートで使っても、設定できる
    - @1=[] という指定は、パートごとに設定するのではなく、全パートで共通で使えることにする
    - @1=[] と設定するたびに、全パートの elapse に送るより、{@1} と Composition 指定されたときに、同時に elapse に送信する


# 実装分析（コード調査に基づく追記）

## 0. 両問題は独立に実装できない ― 追加フレーズ入力機構そのものの再設計が必要

- 問題1「`[]+` が `Part.[]` や `@n=` と併用できない」の原因は、`[]+` の
  文字列連結バッファ (`SeqDataStock.raw_additional`) が
  「どの part / vari 宛か」を記憶していないことにある。
- 問題2「`@n=` が特定パートにしか使えない」の対応は、`@n=[...]` の格納先を
  「part ごとの `pdt[ptnum][n]`」から「part 非依存の共有ストア」へ **種類を
  増やす** 変更である。
- この2つを別々の PR / 別々の設計判断として実装すると、`@1=[]+` の
  ようにバッファと共有Variationが重なった入力で、バッファの宛先は
  「part+vari の組」しか表現できないままになり、`@1=[aaa]+` → `[bbb]` が
  「その時点のカレントパート・Normal フレーズ」に誤って上書きされるという
  **問題1の症状がそのまま再発する**（共有ストア宛という新しい宛先の種類を
  バッファが表現できないため）。
- したがって、必要なのは「問題1を直して、そのあと問題2を足す」という順序
  ではなく、**「[]+ の保留（バッファ）機構を、格納先の種類に依存しない
  形へ一段引き上げる」という再設計を先に行い、その上に (a) part 宛の
  フレーズ設定と (b) 共有 Variation 設定の両方を「保留機構が解決した後の
  ディスパッチ処理」として乗せる**、という構成にする必要がある。

## 1. 再設計方針: 「保留中フレーズ入力」を格納先非依存のコンポーネントに引き上げる

### 現状の問題点（再設計が必要な理由）
- `check_if_additional_phrase()` は `SeqDataStock::set_raw_phrase(part, vari, ...)`
  という **part 別ストレージ (`pdt[ptnum][n]`) 専用の関数の内部** に埋め込まれて
  いる (`seq_stock.rs:101`)。バッファリングという「入力テキストの保留」は
  本質的に格納先（part の pdt か、共有 Variation ストアか）とは無関係な
  処理のはずなのに、いまは part 別ストレージの入口でしか発火しない設計に
  なっている。
- そのため、`@n=` の格納先を `pdt[ptnum][n]` から共有ストアへ変更した瞬間、
  `check_if_additional_phrase()` をどこに置くべきか（`pdt` 側の入口には
  もう `@n=` は来ない）という置き場所の矛盾が生じる。

### 新しい構成
1. `SeqDataStock`（もしくはその手前の `LoopianCmd`）に、格納先を表す
   enum を新設する。

   ```rust
   #[derive(Clone)]
   enum PhraseDest {
       Part(usize, PhraseAs),   // 素の [...]+ / Part.[...]+ / @msr()=[...]+
       CommonVariation(usize),  // @n=[...]+ （問題2で新設する共有ストア宛）
   }
   ```

2. 「保留中の入力」を1箇所にまとめて持つ構造体を新設し、`raw_additional`
   はここに移す。

   ```rust
   struct PendingPhrase {
       dest: PhraseDest,
       raw: String,
   }
   ```
   `SeqDataStock` は `pending: Option<PendingPhrase>` を1つ持つ
   （複数バッファの同時オープンは扱わない方針。理由は後述）。

3. **バッファの開始/継続/解決を、格納先の関数 (`set_raw_phrase` /
   `set_common_variation`) の外側、`LoopianCmd` 側の「コマンド種別ごとの
   処理関数」と「実際の格納・送信処理」の間** に置く。具体的には、
   `apply_phrase_to_part()` (cmdparse.rs:582)、`com_with_part()` の
   `'['` 分岐 (cmdparse.rs:514-528)、`letter_at()` の `@n=` 分岐
   (cmdparse.rs:452-472) が、これまで直接 `put_phrase()` や
   （問題2で新設する）`set_common_variation()` を呼んでいた箇所を、
   共通ゲート関数1つに置き換える。

   ```rust
   // cmdparse.rs 新設
   fn resolve_or_buffer_phrase(
       &mut self,
       dest: PhraseDest,
       tokens: Vec<String>,
   ) -> Result<SetPhraseResult, PhraseCmdError> {
       // 1. 保留中バッファがあれば dest 引数は無視し、
       //    pending.dest を使う（ミスマッチ検知は後述）
       // 2. []+ / rpt()+ を検出したら pending へ追記して return BufferedAdditional
       // 3. 閉じる入力なら combined テキストを組み立て、
       //    pending.dest（または今回の dest）に応じて
       //    put_phrase(part, vari, combined) か
       //    set_common_variation(n, combined) を呼ぶ
   }
   ```

4. `SeqDataStock::set_raw_phrase()` からは `check_if_additional_phrase()`
   の呼び出しを削除し、`set_raw_phrase()` は「もう解決済みの1本の生テキスト
   を part 別ストレージへ格納する」だけの責務に単純化する。同様に、
   これから作る `set_common_variation()` も「解決済みの生テキストを
   共有ストアへ格納する」だけにする。**バッファリングの有無を意識するのは
   `resolve_or_buffer_phrase()` だけ**、という状態にする。

### この再設計によって問題1・問題2がどちらも解決する理由
- `[aaa]+` を素で打った場合 → `dest = Part(self.input_part, Normal)` で
  `resolve_or_buffer_phrase` が呼ばれ、バッファを開く。
- `L1.[aaa]+` を打った場合 → `dest = Part(LEFT1, Normal)` でバッファを開く。
- `@1=[aaa]+` を打った場合 → `dest = CommonVariation(1)` でバッファを開く。
- どの場合も、続く `[bbb]`（素の `[...]`）は `dest = Part(self.input_part, Normal)`
  という「その場の解釈」を持って `resolve_or_buffer_phrase` に来るが、
  **pending が存在する限りこの dest は無視され、pending.dest
  （`Part(LEFT1, Normal)` や `CommonVariation(1)`）が使われる**。
  これにより `L1.[aaa]+` → `[bbb]` も `@1=[aaa]+` → `[bbb]` も、
  最初に確定した宛先へ正しく結合フレーズが届く。
- 格納先が「part 別 pdt」か「共有 Variation ストア」かという **問題2固有の
  分岐は、`resolve_or_buffer_phrase` がバッファを解決した最後の1点だけ**
  に閉じ込められるので、バッファリングのロジック自体（文字列連結・rpt展開）
  は一切変更しなくてよい。

### 併せて解消できる副次バグ
- `com_with_part()` が `L` / `ALL` のような複数パート一括指定で同一
  `rest_vec` を `proper_part` の数だけ `apply_phrase_to_part()` に渡す
  問題 (`cmdparse.rs:525-527`) も、この再設計で自然に解消できる。
  `resolve_or_buffer_phrase` を **パート数分ではなく1回だけ** 呼び、
  `dest` を `Part` 1件ではなく `Vec<PhraseDest>`（複数パート分）として
  持たせ、バッファが解決した時点で対象パート全部へ一括ディスパッチする
  形にすればよい。

## 2. 決定事項(2026-09-07 レビュー反映)

1. **宛先ミスマッチの扱い**: pending 中に「閉じ方向の入力(`]` で終わり
   `+`/`rpt()+` を伴わない)」が来た場合に限り、以下のルールを適用する。
   - 素の `[...]`(part 指定も `@n=`/`@msr()=` も伴わない)なら
     継続とみなし、pending.dest を使って結合する。
   - `Part.[...]` や `@n=[...]` や `@msr(M)=[...]` のように明示的な
     宛先指定を伴う場合はエラーとする。
   - **エラー時、pending は破棄しない。** これは下記2.の「新規オープン時の
     差し替え」とは別ケースであり、閉じるつもりの入力が誤った宛先指定を
     伴っただけと考えられるため、pending をそのまま残し、ユーザーが
     素の `[...]` で正しく閉じ直せるようにする。応答メッセージで
     「@1 のフレーズ入力中です。`[...]` で閉じてください」等、pending
     中であることを明示する。
2. **バッファの多重オープン**: pending が存在する状態で、**明示的な宛先
   指定(`Part.[...]+` / `@n=[...]+` / `@msr(M)=[...]+`)を伴う「開き方向の
   入力」** が新たに来た場合、**前の pending は未完成のまま破棄し、
   新しい入力で pending を差し替える**。同時に2つ以上のバッファを
   保持することはしない(`pending: Option<PendingPhrase>` のまま)。
   - **重要な訂正**: 当初「宛先が pending.dest と同じか異なるかに
     関わらず」と書いたが、これは誤りだった。**素の `[...]+` による
     開き方向の継続(宛先指定なし)は、pending が存在する限り常に
     pending を延長する** — これは `[aaa]+` → `[bbb]+` → `[ccc]` の
     ように、素の `[...]+` を何度でも連続させて同じバッファに連結できる
     という、マニュアル記載の既存機能そのものであり、壊してはならない。
     「差し替え」が起きるのは、**明示的な宛先指定を伴う開き方向の入力が
     来た場合に限る**(例: `L1.[aaa]+` の保留中に `L1.[bbb]+` や
     `L2.[bbb]+` や `@1=[bbb]+` が来た場合)。
   - 実装時は、差し替えが起きたことをユーザーに分かるようにするため、
     通常の "Keep Phrase as being unified phrase!" とは別に
     「前の未完成フレーズ入力を破棄し、新しく入力を開始しました」
     という応答文言を用意することを推奨する(サイレントに消えると
     入力ミスに気づけないため)。
3. **応答文言**: `dest` の種類によって "Keep Phrase..." 系の応答文言を
   変えるか統一するか(`CommonVariation` 宛はまだ elapse に届いていない
   ことが分かる文言にした方が親切)。→ 上記1.・2.のエラー/差し替え文言も
   含め、`dest` と「今回のイベント種別(新規オープン/継続/差し替え/
   エラー)」の組み合わせで応答文言を出し分ける設計とする。
4. **`[]+` をより汎用的な「保留付きフレーズ入力」機構にする**: 当初案では
   `@msr(M)=[...]+` を「Variation と同様に `Part` dest の一種として
   自動的に扱えるはず」という消極的な理由で個別検討していなかったが、
   `PhraseDest::Part(usize, PhraseAs)` は `PhraseAs::Measure(m)` も
   `PhraseAs::Variation(n)` も `PhraseAs::Normal` も同じ enum で表現できる
   ため、**`resolve_or_buffer_phrase()` を経由させれば `@msr(M)=[...]+`
   も追加の特別対応なしにそのまま動く**。つまり `[]+` は「bare / Part. /
   `@n=` / `@msr()=` のどの入口から来ても、同じ保留付きディスパッチを
   通る」という汎用仕様として設計・実装・テストする。`letter_at()` の
   `@msr(M)=` 分岐 (`cmdparse.rs:434-451`) も他の分岐と同様に
   `resolve_or_buffer_phrase(PhraseDest::Part(self.input_part, PhraseAs::Measure(msr)), tokens)`
   を呼ぶ形に統一する。

## 3. 問題2（共有 Variation）側で追加が必要な要素

上記の再設計を前提に、問題2固有で必要になるのは以下のみ。

1. `SeqDataStock` に共有ストア
   `common_vari: [Vec<String>; MAX_VARIATION]` を新設する
   （生トークン列のまま保持。part 固有の `base_note` に依存する
   complement/recombine はまだ行わない）。
2. `set_common_variation(n, combined_text)` を新設し、
   `common_vari[n]` に生テキストを格納するだけの関数にする
   （elapse へは送らない）。
3. `apply_composition_to_part()` (`cmdparse.rs:595-605`) /
   `SeqDataStock::set_raw_composition()` (`seq_stock.rs:174-189`) /
   `CompositionDataStock::set_raw_vec()` (`seq_stock.rs:545-557`) で
   Composition 入力トークンに含まれる `"@n"` を検出し、参照された
   Variation 番号の集合を呼び出し元まで伝播させる。検出ロジックは
   `recombine_to_chord_loop()` 内の `msgs.split('@')`
   (`txt2seq_cmps.rs:319-334`) と同種の走査でよい。
4. 参照された各 `n` について `common_vari[n]` が空でなければ、対象パートの
   `pdt[ptnum][n]` に対して `set_raw_vec()` → `set_recombined()`
   （そのパート固有の `base_note` / `tick_for_onemsr` / `tick_for_beat` を使用）
   を行い、`MessageSender::send_phrase_to_elapse(part_num, PhraseAs::Variation(n), &self.dtstk)`
   でそのパートの elapse に送信する。
5. `@n=` の更新タイミングと既存 Composition への反映タイミングは
   「決定事項」の3.と同様、Composition 設定時のみ同期する
   （即時反映はしない）案を基本とし、マニュアルにその旨明記する。
6. `!clear` 等での `common_vari` クリア処理を追加する。

## 4. テスト

再設計後の `test/test_general.rs` には、少なくとも以下の回帰テストを追加する。
- `[aaa]+` → `[bbb]`（従来通りカレントパートへ結合）
- `L1.[aaa]+` → `[bbb]`（L1 パートへ結合）
- `L.[aaa]+` → `[bbb]`（left1/left2 双方へ結合、二重連結が起きない）
- `@1=[aaa]+` → `[bbb]`（共有 Variation 1 へ結合、どのパートの elapse にも
  即時送信されない）
- `@1=[aaa]+` → 別パートで `{X/@1}` を Composition 指定 →
  そのパートの elapse へ `ElpsMsg::Phr(part, PhrData{vari: Variation(1), ...})`
  が送信される
- `@msr(2)=[aaa]+` → `[bbb]`（Measure(2) 宛に結合、bare 以外の閉じ方入力の
  場合と同様に汎用機構だけで動くことを確認）
- pending 中に素の `[...]` で継続した場合の正常系（`L1.[aaa]+` → `[bbb]`,
  `@1=[aaa]+` → `[bbb]` など、上記「決定事項」1.の継続ルール）
- pending 中に `Part.[...]` や `@n=[...]` など明示的な宛先付きの
  「閉じ方向」入力が来た場合はエラーになり、かつ pending が破棄されずに
  残ること（決定事項1.）
- pending 中に新たな `]+`/`rpt()+` の「開き方向」入力が来た場合、前の
  pending が破棄され、新しい pending に差し替わること（決定事項2.）

## 6. 追加実装(2026-09-10): @n= 更新時に参照済みパートへ自動再送

### 要件
- 上記5.までの実装では、`@n=[...]` の内容は「`{X@n}` が Composition で
  指定された、その瞬間」にしかそのパートの elapse へ送られなかった。
- そのため、`{X@n}` を指定済みのパートがあっても、後から `@n=[...]` の
  内容だけを変更した場合、そのパートへは再送されず、Composition を
  もう一度指定し直さないと更新が反映されなかった。
- 要望: `{X@n}` を送った(=`@n` を参照した)パートを記憶しておき、
  `@n=[...]` が変更された時点で、そのパートへ自動的に再送する。

### 実装
- `SeqDataStock` に `common_vari_subscribers: Vec<Vec<usize>>` を新設。
  index が Variation 番号、値が「現在その Variation を Composition で
  参照しているパート番号一覧」。
- `update_variation_subscription(part, vari_refs)` を新設。
  `apply_composition_to_part()` が Composition 設定の都度呼び、その
  パートを「参照している番号の購読リストに追加」「参照していない番号の
  購読リストからは削除」する。これにより、Composition を書き換えて
  `@n` を参照しなくなったパートは自動的に購読解除される
  (`variation_update_no_resend_after_unsubscribe` テストで確認)。
- `common_variation_subscribers(vari)` で購読中パート一覧を取得できる。
- `dispatch_phrase()` の `PhraseDest::CommonVariation(n)` 解決時
  (`@n=[...]` が確定した時点)に、`common_variation_subscribers(n)` の
  全パートへ `sync_common_variation_to_part()` → `send_phrase_to_elapse()`
  を行うようにした。これで Composition の再指定なしに更新が反映される。
- `clear_part()`(パート単体クリア)でも Composition を `{}` にリセット
  する際に `update_variation_subscription()` を呼び、そのパートを全ての
  購読リストから外すようにした。`clear_common_variation()`
  (`!clear` 相当)でも購読リストごと消去する。

### 追加したテスト(すべて pass)
- `variation_update_resends_to_subscribed_part` — `R1.{X@1}` で購読した
  R1 に対し、Composition を再指定せずに `@1=[...]` だけ変更すると、
  自動的に R1 へ再送される。
- `variation_update_no_resend_after_unsubscribe` — R1 の Composition を
  `@1` を参照しない内容 (`R1.{X}`) に変更した後は、`@1=[...]` を変更しても
  R1 へは送られない。
- `variation_update_no_resend_after_clear_part` — `clear.R1`(パート単体
  クリア)を実行した後は、`@1=[...]` を変更しても R1 へは送られない
  (`clear_part()` が Composition を `{}` にリセットする際、
  `update_variation_subscription()` で購読も一緒に外れることの確認。
  レビューで指摘を受けて追加)。

## （参考）当初の個別分析: []+ が Part.[] や @n= と併用できない問題について

### 現状のコードの動き
- `[]+` の文字列連結処理は `SeqDataStock::check_if_additional_phrase()`
  (`loopian_app/src/cmd/seq_stock.rs`) が担っている。バッファは
  `SeqDataStock.raw_additional: String` という **SeqDataStock に1つだけ存在する
  グローバル状態** であり、どの part / どの vari (Normal/Variation(n)/Measure(m))
  宛に溜めているバッファなのかを一切記憶していない。
- `check_if_additional_phrase()` は `set_raw_phrase(part, vari, input_text)` の
  入口（`seq_stock.rs:101`）でのみ呼ばれる。呼び出し元は3系統ある。
    - (a) 素の `[...]` 入力 → `CmdKind::Bracket` →
      `apply_phrase_to_part(self.input_part, tokens)`
      (`cmdparse.rs:213-215`, `582`)。vari は常に `PhraseAs::Normal`。
    - (b) `Part.[...]` 入力 → `CmdKind::PartWithPayload` →
      `com_with_part()` → `apply_phrase_to_part(pnum, rest_vec)`
      (`cmdparse.rs:499-557`)。vari は常に `PhraseAs::Normal`。
    - (c) `@n=[...]` 入力 → `letter_at()` →
      `put_phrase(self.input_part, PhraseAs::Variation(n), tokens)`
      (`cmdparse.rs:452-472`)。
- マニュアル (`doc/manual.md`) の運用は「`[aaa]+` の後に `[bbb]` を入力する」
  というように、**バッファを閉じる側の入力は素の `[...]` のみ** を想定している。
  つまり `L1.[aaa]+` のように part 指定付きでバッファを開始しても、閉じる側の
  `[bbb]` は必ず経路 (a) を通り、その時点の `self.input_part` と
  `PhraseAs::Normal` で `put_phrase` が呼ばれてしまう。
- 結果として、
    - `L1.[aaa]+` の後にカレントパートが `L1` のままでない状態で `[bbb]` を
      打つと、まったく別パートに結合フレーズが適用される。
    - `@1=[aaa]+` の後の `[bbb]` は `PhraseAs::Normal` 扱いになり、
      `@1` (Variation) として設定されるべきデータが通常フレーズとして
      上書きされてしまう。
  これが「L1. や @1= の場合に使えない」の実体と考えられる。
- さらに、`com_with_part()` は `L`（left1+left2）や `ALL` のように複数パートを
  一括指定した場合、`proper_part` を `for` ループしながら **同一の `rest_vec`
  を複数回** `apply_phrase_to_part()` に渡す (`cmdparse.rs:525-527`)。
  `]+` を含む入力だとループ2周目以降も `check_if_additional_phrase()` が
  呼ばれ、同じ文字列が `raw_additional` に二重・三重に連結されてしまう
  （1周目で `raw_additional` が空でなくなるため、2周目は「2回目以降」の
  分岐に入ってしまう）。これは `L1.[...]+` 単体よりもさらに顕著な破綻。

### 実装方針
1. `SeqDataStock` に `raw_additional` と対にして、バッファ開始時点の宛先
   `additional_target: Option<(usize /* part */, PhraseAs /* vari */)>`
   を保持するフィールドを追加する。
2. `]+` を検出した最初の入力の時点で `additional_target` に
   `(part_num, vari)` を記録する。新仕様の「先に []+ の処理を行い、内容を
   バッファに保持、次回の [] が来るまで待つ」に対応する部分であり、
   `Part.[]` や `@n=` としての解釈（part 決定・vari 決定）は行うが、
   `set_raw_phrase` 内の complement / recombine / elapse 送信までは
   進めない、という現在の `BufferedAdditional` の考え方はそのまま踏襲できる。
3. バッファを閉じる入力（`]` で終わり `+` を伴わない入力）を受け取った際は、
   その入力自体がどの経路 (a)/(b)/(c) から来たかに関わらず、
   `additional_target` に記録された `(part_num, vari)` を **優先して**
   `put_phrase()` を呼ぶようにする。マニュアル通り「閉じる側は素の `[...]`
   のみ許容する」仕様のままでよいが、内部的な宛先解決を
   「その場の呼び出し引数」から「バッファ開始時に記録した宛先」に変更する。
4. 複数パート一括指定 (`L.[...]+`, `ALL.[...]+` 等) の二重連結バグに対応する
   ため、`]+` を検出したら `proper_part` のループを1回で打ち切る
   （もしくは `additional_target` を `Vec<(usize, PhraseAs)>` にして
   複数パート分をまとめて記録し、バッファが閉じた時点で全パートへ
   一括適用する）。
5. `apply_phrase_to_part` / `letter_at` の戻り値・応答文言
   （`"Keep Phrase as being unified phrase!"`）は変更不要だが、内部的には
   「これは新規バッファ開始か、既存バッファへの継続/終端か」を
   `SeqDataStock` 側で判定できるようにする必要がある。
6. `test/test_general.rs` に、`L1.[aaa]+` → `[bbb]` の順で入力した際に
   L1 パートへ結合フレーズが送られること、`@1=[aaa]+` → `[bbb]` の順で
   Variation(1) として結合フレーズが送られること、`L.[aaa]+` → `[bbb]`
   で文字列が二重連結されないこと、をそれぞれ回帰テストとして追加する。

## （参考）当初の個別分析: @n= が特定パートにしか使えない問題について

※ 以下の「実装方針」は再設計前の初稿。実際の対応は上記「3. 問題2（共有
   Variation）側で追加が必要な要素」を参照。現状コードの調査内容は変わらず
   有効なので記録として残す。

### 現状のコードの動き
- `letter_at()` の `@n=` 分岐 (`cmdparse.rs:452-472`) は
  `put_phrase(self.input_part, PhraseAs::Variation(n), tokens)` を直接呼ぶ。
  `SeqDataStock::set_raw_phrase()` は part ごとに分かれた
  `pdt: Vec<Vec<PhraseDataStock>>`（`pdt[ptnum][n]`）にデータを格納し、
  その場で `complement_phrase` / `set_recombined`（そのパート固有の
  `base_note` を使用）まで行い、`MessageSender::send_phrase_to_elapse()`
  経由で **そのパートの elapse スレッドにのみ** `ElpsMsg::Phr` を即時送信する
  (`cmdparse.rs:606-628`)。つまり `@n=[...]` は最初から
  「カレントパート専用の Variation データ」として設計されている。
- 一方、`{X/@n}` のような Composition 指定は `CompositionDataStock`
  (`cdt: [CompositionDataStock; MAX_INST_PART]`、こちらもパートごとに独立)
  の中で `recombine_to_chord_loop()` (`txt2seq_cmps.rs:317-334`) が
  `"@n"` トークンを検出して `CmpEvt::Vari(VariEvt{tick, vari:n})` を
  そのパートの chord イベント列に埋め込むだけである。
- 再生時は `elapse_part.rs::check_variation()` →
  `cmps_map.rs::get_vari_num()/gen_vari_num()` が発火すると、
  **そのパート自身** の `phr_loop_mng::reserve_vari(vari_num)`
  (`elapse_loop/phr_loop_mng.rs:295-297`) が呼ばれ、`exists_vari_phr()`
  (`phr_loop_mng.rs:609-611`) で「そのパートの elapse に既に送信済みの
  `PhraseAs::Variation(vari_num)` フレーズ」を検索して再生予約する。
- つまり Variation フレーズは **各パートの elapse 側に事前送信されている
  ことが前提** になっており、`@1=[...]` を入力した瞬間のカレントパート以外の
  `phr_loop_mng` にはそのフレーズが存在しないため、他パートで `{@1}` を
  指定しても何も再生されない。これが「特定パートにしか使えない」の実体。

### 実装方針
1. `SeqDataStock` に、part 非依存の共有バッファ
   `common_vari: [Vec<String>; MAX_VARIATION]`
   （1問目の `[]+` バッファリング機構を流用できるよう、生トークン列のまま
   保持する）を新設する。`@n=[...]` の入力はここに保存するだけとし、
   従来のように特定パートの `pdt[ptnum][n]` へ complement / recombine /
   elapse 送信まで行うのはやめる。
2. `apply_composition_to_part()` (`cmdparse.rs:595-605`) /
   `SeqDataStock::set_raw_composition()` (`seq_stock.rs:174-189`) /
   `CompositionDataStock::set_raw_vec()` (`seq_stock.rs:545-557`) の
   いずれかで、Composition 入力トークンに含まれる `"@n"` を検出し、
   参照された Variation 番号の集合を戻り値として呼び出し元
   （`apply_composition_to_part`）まで伝播させる。検出ロジックは
   `recombine_to_chord_loop()` 内の `msgs.split('@')` と同種の走査を、
   `complement_composition()` 適用後のトークン列に対して先読みで行えばよい。
3. 参照された各 `n` について、`common_vari[n]` が空でなければ、
   対象パート用の `pdt[ptnum][n]` に対して
   `set_raw_vec(common_vari[n].clone(), ...)` → `set_recombined(...)`
   （そのパート固有の `base_note` / `tick_for_onemsr` / `tick_for_beat` を使用）
   を行い、`MessageSender::send_phrase_to_elapse(part_num, PhraseAs::Variation(n), &self.dtstk)`
   でそのパートの elapse に送信する。これが新仕様3点目
   「{@1} と Composition 指定されたときに、同時に elapse に送信する」に対応する。
4. 反映タイミングの仕様決めが必要: `@1=[...]` の内容を後から更新した場合、
   既に `{@1}` を参照済みの他パートへ即座に再送するのか、次にその
   パートの Composition を再入力するまで反映しないのか。実装コストが
   低いのは後者（Composition 設定時のみ同期）だが、その場合は
   「`@n=` を更新しても、既にセット済みの Composition には反映されない」
   という制約をマニュアルに明記する必要がある。
5. `!clear` などパート/全体クリア時に `common_vari` 自体をクリアする
   処理（`clear_part()` / `del_raw_phrase()` とは別に）を追加する。
6. `test/test_general.rs` に、`@1=[...]` を入力した後、別パートで
   `{X/@1}` を Composition 指定した際にそのパートへ
   `ElpsMsg::Phr(part, PhrData{vari: Variation(1), ...})` が送信される
   ことを確認する回帰テストを追加する。
